# Google Meet recording bot MVP

## Goal and scope

A user pastes a Google Meet link into the local web app. One bot, running on the same Linux machine as the API and meeting worker, joins as a visible participant using a dedicated Google account and Chrome profile. The host admits it when Meet requires approval. The bot records meeting audio, closes a new audio part at most every 30 minutes, and sends the ordered parts through the existing AI pipeline as one meeting with a continuous transcript.

The first release supports Google Meet only and one active bot session per machine. It starts recording only after the bot has joined. It stops when the user presses **Stop bot** or the meeting ends. It does not automatically rejoin after a disconnect. The user is responsible for informing participants that the bot records audio; the bot's display name is **Meeting AI Recorder**. The capture method does not use Meet's own recording control or imply that Meet will show its recording indicator.

Zoom, Teams, calendar scheduling, video capture, real-time transcription, cross-part speaker identity matching, and cloud deployment are outside this release.

## Recommended approach and constraints

Use a separate Chrome process with a persistent, private profile for the bot account. The operator signs in once interactively; the application never stores the Google password or recovery codes. A dedicated local audio output routes only this Chrome process to an FFmpeg capture input. The recorder must verify that the dedicated output is available before it joins; it must never fall back to recording the machine's default output. The browser and recorder run in a separate bot runner process so API restarts do not end an active call. The existing inference worker remains separate and starts only after capture is finalized. Browser UI changes and account challenges can interrupt joining; the runner reports those states instead of claiming a recording started.

Chrome is [supported by Google Meet](https://support.google.com/meet/answer/7317473). A guest or outside participant may still need [admission by someone in the meeting](https://support.google.com/meet/answer/9303069/join-a-meeting); a valid URL alone cannot guarantee entry. The Chrome profile is distinct from the user's normal profile, following [Playwright's persistent-profile guidance](https://playwright.dev/docs/api/class-browsertype). The local audio implementation must be proved on the target machine before the browser runner is considered ready.

## Components and data flow

1. The web app submits a Google Meet URL and optional title to a local-only bot-session API. The API checks the exact `meet.google.com` host, HTTPS scheme, acceptable Meet path, and the one-session limit. It creates a durable session request without opening the URL in the API process.
2. A dedicated bot runner claims that request under a process-wide file lock. It checks Chrome, the private profile, the dedicated audio output, FFmpeg, and available storage. It opens the URL with mic and camera off. The UI reports `joining` and, when applicable, `waiting_admission`.
3. Once the runner confirms admission, it starts capture and records the session start time. It records 16 kHz mono PCM WAV and rolls to a new part before 1,800 decoded seconds, leaving a small margin for recorder timing. A completed part is published atomically to private storage and registered with its ordinal, capture start offset, duration, and storage key. The active, unfinished part is never exposed to inference.
4. A normal stop closes the final part, leaves Meet, and creates one `google_meet_bot` meeting referencing all completed parts. It queues the existing AI worker. If no finalized part contains decodable audio samples, it creates no meeting and reports a safe failure. Silence is still valid recorded audio.
5. The worker decodes and processes one part at a time using the current VAD, language routing, ASR, and diarization pipeline. It offsets segments by each part's recorded start position on the session timeline and writes one combined transcript/result. If a gap occurred between recorded parts, that gap remains in timestamps.

The bot runner never calls model inference. The existing `POST /api/meetings` upload path, `/api/audio/process`, and their limits retain their current behavior.

## State and recovery

Bot sessions use `queued`, `joining`, `waiting_admission`, `recording`, `finalizing`, `completed`, `interrupted`, and `cancelled`. `completed` means that the session has produced a queued meeting; the meeting's existing status then reports AI processing. A user stop during `joining` or `waiting_admission` cancels the session without creating a meeting. The runner has a bounded admission timeout and reports a safe failure code when it expires.

Browser exit, loss of the audio device, FFmpeg failure, disk exhaustion, or runner exit marks an active session `interrupted`. On runner startup, stale active sessions are recovered to `interrupted`, without automatic rejoin. The UI can offer **Process recorded parts** when one or more finalized parts exist, or **Discard recording**. Processing partial audio creates one meeting and records that capture ended early; it never claims the missing interval was transcribed. Both finalization actions are idempotent. An unfinished part can be discarded during recovery; finalized parts remain until the user processes or discards them.

Only one bot session may occupy the recorder at a time, enforced in the database and by a host-level lock so multiple API or runner processes cannot bypass it. A stop request is durable; the runner observes it and closes capture. Cancelling/discarding removes stored audio for that session. Deleting the resulting meeting removes all its audio under the existing deletion contract and removes or redacts the associated session URL.

## Storage and API contracts

The existing SQLite database gains a durable `bot_sessions` table for URL, safe status/failure code, timestamps, stop request, and resulting `meeting_id`, plus a `bot_session_parts` table for finalized part metadata. This is session state in the current database, not a new cache service. Audio bytes remain in private files, not SQLite. Part publication and registration use the existing publication lock. Finalization attaches those existing files to the new meeting without rewriting audio bytes, then removes their session-part references in the same transaction. Orphan cleanup must consider both session-part and meeting-part references. The URL is needed only while joining or recording; it is cleared after finalization or discard. The bot's Chrome profile lives in a separate private directory, is ignored by Git, and is not included in meeting exports or logs.

The `meetings` table gains a source value with `upload` as the default for existing rows and `google_meet_bot` for bot recordings. `meeting_audio_files` gains `start_seconds`; existing uploaded parts derive starts from cumulative decoded durations, while bot parts use capture offsets. Meeting list and detail add `source`; meeting detail adds `audio_files[].start_seconds`, without removing current response fields. The web player's seek mapping uses `start_seconds`, so it can show gaps correctly. Uploads continue to have at most 10 files, 100 MiB total, and 30 minutes combined. Bot recordings have no upload request and may contain more parts or exceed 30 minutes combined; each individual part must stay within the decoder's 30-minute limit. Storage errors stop capture and preserve already finalized parts.

The local-only API adds `POST /api/bot-sessions`, `GET /api/bot-sessions/active`, `GET /api/bot-sessions/{id}`, `POST /api/bot-sessions/{id}/stop`, `POST /api/bot-sessions/{id}/process-parts`, and `DELETE /api/bot-sessions/{id}` for discard. Creation accepts a canonical `https://meet.google.com/xxx-xxxx-xxx` link and optional title; it strips query and fragment before storage and rejects other hosts or path forms. Creation returns a session ID; once finalized, status also returns the meeting ID. Repeated create calls with the same optional `Idempotency-Key` resolve to the same session; a second distinct active request returns a conflict. These endpoints reuse the meeting library's loopback, Host, and Origin restrictions. Responses expose safe status codes, not credentials, private file paths, or raw provider errors.

The current meeting worker's combined 30-minute check applies to `upload` meetings only. It processes bot parts sequentially and uses persisted offsets rather than assuming contiguous audio. Existing speaker labels remain distinct by part; the MVP makes no cross-part speaker identity claim.

## User interface

The local web app adds a Google Meet link form and one active-session panel. It shows `joining`, `waiting_admission`, `recording`, `finalizing`, `interrupted`, and `completed`, plus elapsed time and finalized-part count. Before starting, it tells the user to inform participants that audio will be recorded and that a host may need to admit the bot. It provides **Stop bot**, **Process recorded parts**, and **Discard recording** only when their states allow them. After finalization, it navigates to the single meeting detail page; that page shows ordered audio parts and a continuous transcript.

## Verification and operational requirements

Focused tests cover URL validation, admission and stop transitions, one-session locking, timeouts, failed capture, atomic part publication, recovery after process death, idempotent finalization, deletion, and private-data-safe errors. Existing upload API tests must keep passing. Worker tests cover a bot meeting longer than 30 minutes, more than 10 parts, per-part duration rejection, gaps in offsets, transcript order, and unchanged upload limits. Browser behavior is tested with a fake adapter; no fast test downloads models or joins a live Meet.

An operator-run smoke test on the target machine must establish that Chrome can join a test Meet, the host can admit the bot, the dedicated audio output captures only the bot's call audio, and a finalized part reaches the existing worker. An accelerated segment interval tests rollover and one-meeting assembly; it is not an ASR quality benchmark. Before describing model quality, run held-out audio evaluation and record model IDs, preprocessing, latency, and WER/CER or VAD/DER/JER as relevant. Any later model or preprocessing change follows the project's evaluation gate.

Setup documentation must name the required Chrome binary, local audio server and virtual-output setup, bot profile location, FFmpeg, new settings, and three processes (API, bot runner, inference worker). The first release is supported on the local Linux machine only. It needs migration and rollback notes because it adds SQLite tables and columns; rollback stops all processes and preserves or exports the data directory before reverting code. Existing meeting files and API behavior remain readable after migration.
